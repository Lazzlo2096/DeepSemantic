# Выводы замеров эмбеддингов OpenRouter / DeepInfra

Дата анализа: 12 ноября 2026 года.

## Основной результат

Среди проверенных конфигураций лучший результат по суммарной скорости показал
**батч 128 чанков и до 8 одновременно выполняемых запросов**.
В трёх повторах эта конфигурация обработала все 12 288 отправленных чанков:
96 HTTP-запросов, 0 ошибок. Скорость составила **286,81 чанка/с**.
Скорости отдельных повторов: 281,8 / 288,4 / 290,3 чанка/с.
Каждый повтор обрабатывал 4096 чанков примерно за 14,1–14,5 секунды.

Это лучший проверенный кандидат для фоновой индексации через DeepInfra.
Ноль ошибок означает отсутствие потерь в данном замере, а не гарантию
безошибочной работы в будущем. Качество семантического поиска тест не измерял.

## Условия

- Прогон: `results/20261112T094557.823457Z/`.
- Источники: `metadata.json`, `summary.json`, `requests.jsonl`.
- Модель в запросе: `baai/bge-m3`; провайдер закреплён как `deepinfra`.
- Переключение на других провайдеров отключено.
- Батчи: 128, 256, 512 чанков; параллельность: 2, 4, 8 запросов.
- 4096 одинаковых входных чанков на каждый вариант, по три повтора.
- Тексты синтетические, около 203 токенов на чанк по возвращаемому usage.
- Порядок прогонов перемешан; между ними пауза 3 секунды.
- Автоматических повторов неудачных запросов нет; таймаут 60 секунд.

## Что удалось установить об ошибках 429

Прогоны могли влиять друг на друга: пауза 3 секунды не гарантирует
восстановление квоты или доступной мощности. Перемешивание порядка
не устраняет этот эффект.

Постоянный общий лимит 50–60 запросов/минуту не подтверждается.
В предыдущем прогоне `20261112T093146.832378Z` вариант `8 × 4`
успешно выполнил 120 запросов за 30,6 секунды.
Восстановленная шкала показывает до 163 успешных отправок за 60 секунд.

Единый постоянный лимит токенов за минуту также не объясняет результаты.
Для той же конфигурации `256 × 8` запросы успешно проходили при накопленной
нагрузке около 2,49 млн токенов за 60 секунд, но получали 429 при 1,32–1,40 млн.
Расчёт учитывает токены успешных отправок за предыдущее окно плюс текущий запрос.
Количество токенов отказавших запросов восстановлено по их успешным повторам
на тех же входных текстах; значения usage между повторами совпали.

Проверки скользящих окон от 5 до 300 секунд, календарных минут и
накопительной квоты с постепенным восстановлением не дали единого
удовлетворительного объяснения всех отказов.
Время запросов восстановлено по порядку завершения и длительностям;
расхождение с полной длительностью прогонов — менее 0,05 секунды на прогон.
Моменты фактического принятия запросов сервером неизвестны.

Причина 429 не установлена. Возможны меняющаяся доступная мощность,
общая нагрузка других клиентов или ограничения отдельных обслуживающих узлов.
Данные не позволяют вывести устройство GPU, очередей или точные квоты провайдера.
Тело ошибки скрипт не сохранял; Retry-After у этих отказов отсутствовал.

## Применение результата

Для следующей проверки фоновой индексации использовать батч 128 и лимит
8 одновременных запросов к DeepInfra. Сохранять статус каждого чанка и
повторять временные ошибки с задержкой, учитывая Retry-After при его наличии.
При серии 429 уменьшать нагрузку. Поиск пользователя обслуживать без
ожидания заполнения больших батчей.

Производственный код на момент замеров индексирует батчи последовательно,
а embedding service использует RabbitMQ prefetch_count=1. Для получения
измеренного выигрыша необходимо отдельно реализовать параллельную обработку
в режиме OpenRouter и согласовать лимит на весь сервис.
Размер 128 также превышает текущий лимит API в 32 текста на запрос:
перед применением потребуется обновить ограничения входа.
Настройки локальной модели следует подбирать отдельно.

Следующая валидация: реальные чанки и длительный непрерывный прогон `128 × 8`
с записью времени начала/окончания запросов и диагностических полей ошибок.
Вывод относится к исследованным размерам текстов, модели, провайдеру и времени
замера; больший размер чанков или другая нагрузка могут изменить результат.
