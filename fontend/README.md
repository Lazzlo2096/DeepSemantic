# Каталог статей arXiv

Из корня DeepSemantic запусти `docker compose up -d fontend` и открой страницу каталога. При необходимости порт задаётся переменной `FONTEND_PORT`. [Локальный каталог](http://127.0.0.1:8080)

## Развёртывание на deep-semantic.com

На Ubuntu запусти `sudo bash bootstrap.sh` из корня проекта. Запись DNS для `deep-semantic.com` должна указывать на публичный адрес сервера, а TCP-порты 80 и 443 должны быть свободны и доступны из интернета. Caddy выпустит и будет обновлять сертификат автоматически. [Каталог на сервере](https://deep-semantic.com)

Укажи в `.env` ключ `OPENROUTER_API_KEY` и выбери модели `RAG_OPENROUTER_MODEL` и `SUMMARY_OPENROUTER_MODEL`. Затем запусти `sudo just up-server`. Генерация выполняется через OpenRouter. Для эмбеддингов `EMBEDDING_PROVIDER=deepkaravan` выбирает локальный контейнер без API-ключа, `EMBEDDING_PROVIDER=openrouter` — OpenRouter с ключом `OPENROUTER_API_KEY`. Оставь `EMBEDDING_BASE_URL` пустым для автоматического выбора адреса.

Управление путями обработки доступно на странице [Воркеры на сервере](https://deep-semantic.com/workers.html).

## Авторизация

Caddy оставляет каталог и готовые материалы публичными. RAG и векторный поиск требуют входа. Импорт arXiv, ручной запуск суммаризации, настройки пайплайна, управление контейнерами и страница пользователей требуют роль `admin`.

Запросы входа и управления аккаунтами Caddy передаёт в `auth-service`. Перед защищённым запросом `forward_auth` проверяет сессию, после чего основной FastAPI получает подтверждённые ID, адрес и роль пользователя. История RAG доступна только создавшему её аккаунту.

Первого администратора создайте после миграций:

```sh
docker compose run --rm auth-service python -m auth_service.cli create-admin admin@example.com
```

На сервере задайте `AUTH_PROXY_SECRET` в `.env`. Ссылка для следующего пользователя создаётся на странице `/users.html` и содержит одноразовый токен приглашения.

## Работа с каталогом

Страница читает `GET /papers` через локальный прокси Caddy и показывает заголовки, авторов, даты подачи и аннотации. Каталог показывает по 12 записей на странице и общее число страниц для выбранных фильтров.

Чипс «Текст извлечён» означает наличие Markdown, а не готовность чанков или
эмбеддингов. Каталог и страница статьи показывают два независимых чипса:

- «Статья в Qdrant» — все актуальные чанки полного текста найдены в Qdrant.
- «Саммари готово · индексируется» — актуальный текст саммари уже доступен, но не все его чанки ещё найдены в Qdrant.
- «Саммари готово · в Qdrant» — актуальное саммари и все его чанки доступны в Qdrant.

До завершения соответствующей ветки показаны «Индекс статьи не готов» и
«Саммари не готово». Если текст уже создан, а Qdrant недоступен, чипс отдельно сообщает о недоступности индекса.
Готовность статьи не зависит от того, отложена ли суммаризация. Проверка
выполняется на сервере при загрузке каталога или статьи, с учётом текущих версий
исходников, модели, промпта и параметров чанкинга. API возвращает `article_index`
и `summary_index` с `status` (`pending`, `completed`, `unavailable`),
`chunks_total` и `chunks_in_qdrant` (`null`, если проверить Qdrant не удалось).
Проверяются реальные точки, в том числе обнаруживается их удаление напрямую
из Qdrant; ссылки PostgreSQL сами по себе не дают статус `completed`.
Состояние отражает момент проверки, а для обновления чипсов обновите страницу.
Фильтр «Текст саммари» проверяет наличие текста, независимо от его индексации.

В фильтре «Статус» есть пункт «Статья в Qdrant»:
`GET /papers?status=article_index_completed`. Он выбирает документы с
`article_index.status == "completed"` по всему каталогу до пагинации, учитывает
остальные фильтры и сортировку и возвращает отфильтрованный `X-Total-Count`.
Проверяется реальное наличие точек в Qdrant; состояние саммари не влияет на
результат. Если проверить непустой индекс не удалось, API возвращает 503,
а не исключает документ из результатов. Проверка выполняется порциями по 100 статей;
на большом каталоге этот фильтр требует дополнительного времени.

Заголовок в каталоге и результатах поиска открывает страницу статьи. Администратору на ней доступен выключенный по умолчанию переключатель `Debug mode`: он показывает секцию «Чанки статьи» и подгружает чанки в исходном порядке из защищённого `GET /papers/{arxiv_id}/chunks`. Выбор сохраняется в браузере. Для остальных пользователей переключатель и секция скрыты, а endpoint чанков требует роль администратора. Ссылка «arXiv ↗» рядом с заголовком открывает оригинал в новой вкладке.

Обработчик суммаризации в `temporal-orchestrator` автоматически создаёт задание для статьи, когда доступен Markdown. Кнопка «Суммаризировать» также позволяет запустить его вручную. Страница опрашивает `GET /papers/{arxiv_id}/summary` и показывает прогресс или сохранённый результат на русском. Повторный запрос возвращает существующее задание или готовый результат. После ошибки кнопка «Повторить» ставит задание заново.

Обработчик суммаризации в `temporal-orchestrator` читает полный Markdown из RustFS и отправляет его вместе с промптом одним запросом. Промпт запрашивает объяснение на русском объёмом 700–1000 слов и шесть разделов от главной идеи до практического значения. Для суммаризации нужен импорт в режиме HTML.

Для суммаризации и ответов RAG укажи `OPENROUTER_API_KEY` в `.env`. Модель для RAG задаётся через `RAG_OPENROUTER_MODEL`, по умолчанию `deepseek/deepseek-v4.1-flash-1017`. Для суммаризации можно задать `SUMMARY_OPENROUTER_MODEL` и `SUMMARY_OPENROUTER_REASONING_EFFORT`. Если модель суммаризации не задана, воркер берёт модель RAG. В `.env.example` для воркера указаны `deepseek/deepseek-v4-pro-0813` и `high`. Провайдер эмбеддингов выбирается через `EMBEDDING_PROVIDER`, адрес при необходимости переопределяется через `EMBEDDING_BASE_URL`. После изменения `.env` пересоздай соответствующий контейнер.

Для суммаризации через OpenRouter действуют лимиты провайдера. PostgreSQL хранит статус и итоговый Markdown в `paper_summaries`, по одной записи на версию статьи.

При обновлении работающего стека с `paper-summarizer` сначала выполни `docker compose down --remove-orphans` с тем же набором Compose-файлов, затем запусти проект в своём режиме. Тома и задания суммаризации сохранятся.

Сортировку можно выбрать по времени загрузки, дате подачи или этапу обработки. Фильтры по статусу и дате подачи можно использовать вместе. Границы диапазона включаются целиком по UTC. API принимает `sort` (`downloaded_desc`, `submitted_desc`, `submitted_asc`, `status`), `status`, `date_from` и `date_to` (`ГГГГ-ММ-ДД`).

Каталог сохраняет фильтры, сортировку и номер страницы в URL, например `/?status=texted&sort=submitted_desc&page=2`. Ссылка с `query` сразу запускает поиск в режиме из параметра `mode` (`vector`, `text` или `rag`). Без `mode` используется поиск по RAG. Кнопка «Вернуться к каталогу» восстанавливает параметры каталога.

- «Поиск по RAG» отправляет запрос в `POST /rag/answer`. Модель вызывает векторный или текстовый поиск и читает исходный текст статьи или суммаризации по координатам. Контекст и объём генерации определяются настройками модели и провайдера. Ответ показывает ссылки на подтверждающие фрагменты и пояснение их выбора. Блок «Как найден ответ» обновляется примерно раз в секунду и показывает завершённые шаги модели, доступный текст рассуждения от провайдера и карточки инструментов с аргументами, результатами и временем. Ссылка на запуск открывает сохранённую историю через `GET /rag/runs/{run_id}`. Выбранная модель должна поддерживать вызов инструментов и структурированный вывод.
- «Векторный поиск по эмбеддингам» вызывает `POST /chunks/search` и показывает похожие фрагменты с оценкой сходства.
- «Текстовый поиск» вызывает `POST /chunks/search/text`. PostgreSQL ищет введённую строку без учёта регистра внутри сохранённых чанков. Поиск доступен после разбиения текста на чанки, даже если для них ещё нет эмбеддингов.

На странице «Импорт arXiv» можно отправить `POST /arxiv/imports` с диапазоном дат и необязательным фильтром. API выбирает бакет по умолчанию. История из `arxiv_imports` читается через `GET /arxiv/imports`, показывает статус, попытки и результаты и обновляется каждые пять секунд на открытой вкладке. [Импорт arXiv](http://127.0.0.1:8080/imports.html)

Команды `just up` и `just up-server` автоматически запускают все обработчики
в одном контейнере `temporal-orchestrator`. Отдельный запуск оркестратора:

```sh
docker compose up -d temporal-orchestrator
```

На сервере добавь `-f compose.yaml -f compose.server.yaml` после `docker compose`.
Страница [Воркеры](http://127.0.0.1:8080/workers.html) управляет путями обработки;
кнопки запуска и остановки контейнеров удалены.

На странице «Воркеры» блок «Пути обработки статей» управляет глобальным режимом
суммаризации через `GET/PUT /pipeline/settings`. Кнопка «Отложить саммари»
оставляет только HTML → Markdown → чанки статьи → эмбеддинги → Qdrant.
Кнопка «Включить саммари» включает также генерацию и индексацию саммари и
обработку накопившихся статей. Настройка сохраняется после перезапуска;
для выполнения обработки нужен работающий `temporal-orchestrator`.
Уже начавшийся вызов модели или батч может завершиться после переключения.

Рядом показываются состояние фоновой сверки, ошибки и накопительные счётчики
из `GET /pipeline/summary-reconciliation`, обновляемые каждые пять секунд.
Число запусков не означает число готовых саммари. Готовность отдельной ветки
проверяется через `GET /papers/{arxiv_id}/processing`. На странице статьи
отложенное саммари показано с пояснением и ссылкой на настройки; после
включения статус обновляется автоматически.
