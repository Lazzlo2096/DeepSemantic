# Архитектурный разбор DeepSemantic

Дата: 12 ноября 2026 года. Область: текущий код API, воркеров, миграций, Compose и потребителей состояния во frontend.

Это статическое исследование: сценарии ниже выведены из SQL и порядка операций. Стек не запускался, сбои на работающей БД не воспроизводились, содержимое серверных резервных копий и секреты не исследовались. Код приложения не изменён. Приоритет означает важность устранения, а не подтверждение, что проблема уже случалась на сервере.

## Главный вывод

В проекте различается не только способ постановки в очередь. Различаются правила актуальности результата, восстановления после сбоя, повторных попыток и идентичности задания. Именно эти различия опаснее разных схем таблиц.

Не обязательно превращать все таблицы в одинаковые очереди. Имеет смысл унифицировать контракт обработки: что делает работу необходимой, какая версия входа обрабатывается, кто владеет попыткой, когда результат считается актуальным и как восстанавливается фактически потерянный результат.

## Как фактически устроена обработка

| Этап | Что хранится | Что делает работу доступной | Как фиксируется результат |
| --- | --- | --- | --- |
| Импорт | `arxiv_imports` — явное задание; `arxiv_import_attempts` — попытки | INSERT задания с `queued` | Статус задания и счётчики попытки; статьи сохраняются независимо по мере загрузки |
| Извлечение текста | `arxiv_papers` — одновременно каталог и состояние обработки | `downloaded` + HTML + наступивший `text_available_at`; также просроченный `texting` | `text_object_key`, `texted`, очистка аренды |
| Суммаризация | `paper_summaries` — одновременно задание и единственный результат статьи | API создаёт строку; воркер также сам создаёт её для подходящей статьи | `completed` и `summary` в той же строке |
| Разбиение | Источники вычисляются представлением `paper_chunk_sources` | Нет нулевого чанка нужной версии с координатами | Набор `chunks` + `paper_chunks` |
| Эмбеддинги статей и саммари | Отдельной таблицы заданий нет | Ссылка в `chunks` отличается от ожидаемой коллекции/ID | Вектор в Qdrant, затем ссылка в PostgreSQL |
| Ручной чанк | Только `chunks` | INSERT сам по себе ничего не запускает; нужен POST embedding | Синхронная запись в Qdrant и PostgreSQL |
| RAG | `rag_runs` — история синхронного HTTP-запроса | Исполняется непосредственно обработчиком запроса | Запись терминального статуса обработчиком |

Источники: `api/main.py:115`, `arxiv-grabber/text_worker.py:43`, `summary-worker/main.py:93`, `api/paper_embeddings.py:31`, `api/chunks.py:181`, `api/rag.py:385`.

Два уточнения к исходному наблюдению:

- Даже создание `arxiv_papers` не всегда означает очередь извлечения: PDF остаётся `downloaded`, но HTML-воркер его не берёт.
- Отсутствие `paper_summaries` не означает отсутствие будущей работы: включённый воркер сам постепенно материализует задания. Поэтому число строк `queued` не равно всему ожидающему объёму суммаризации.

## 1. Саммари не привязано к версии текста — высокий приоритет

**Факт.** При смене выбранного исходника `save_paper` сбрасывает `text_object_key`, аренду и статус статьи, но не инвалидирует `paper_summaries`. Саммари идентифицируется только `arxiv_id`. В отличие от чанков, у него нет версии входного текста.

**Сценарий A:** готовое саммари → выбран другой исходник/бакет или сменился формат → повторно извлечён текст. Старое саммари остаётся `completed`. Автовыборка исключает статью, потому что строка саммари уже существует. POST summary пересоздаёт только `failed`, а готовый результат возвращает как есть.

**Сценарий B:** воркер захватил старый Markdown → исходник статьи заменён → воркер завершил запрос к LLM. Проверка `ACTIVE_LEASE` сверяет ID задания, номер попытки, статус и срок аренды, но не входную версию статьи. Устаревший результат может быть опубликован.

**Последствие.** `has_summary=true` и summary-чанки могут относиться к прежнему тексту, тогда как article-чанки уже относятся к новому. Тот же arXiv ID не гарантирует одинаковую извлечённую репрезентацию при изменении формата или обработки.

**Основания:** `arxiv-grabber/main.py:299`, `summary-worker/main.py:90`, `summary-worker/main.py:100`, `summary-worker/main.py:201`, `api/paper_summaries.py:48`, `api/paper_summaries.py:58`, `api/papers.py:109`, `postgres/migrations/versions/0031_paper_chunk_sources.py:24`.

**Рекомендация.** Фиксировать `input_version` при захвате задания и проверять её перед публикацией. Определять актуальность саммари через соответствие текущему тексту. При новом входе создавать новую генерацию результата или явно инвалидировать старую; завершение прежней попытки не должно публиковать её как текущую.

## 2. Изменение настроек не имеет общего правила инвалидирования — высокий/средний приоритет

**Факт.** `PENDING_SOURCES` проверяет версию содержимого и наличие координат нулевого чанка. Параметры разбиения и версия алгоритма не участвуют. `EMBEDDING_MAX_TOKENS` читается позже, но уже подготовленный источник не попадёт в разбиение только из-за изменения этого значения.

**Сценарий:** сначала разбить по 512 токенов, затем настроить 256 и перезапустить воркер. Старые источники сохранят прежнюю разбивку, новые получат другую. Если новая модель требует меньших фрагментов, переиндексация может постоянно отвергать старые чанки.

У суммаризации `model` и `prompt_version` записываются для диагностики, но их изменение не возвращает `completed` в работу. У эмбеддингов смена имени модели меняет коллекцию и запускает обработку связанных чанков. Получается три разных смысла изменения конфигурации.

**Основания:** `api/paper_embeddings.py:31`, `api/paper_embeddings.py:227`, `summary-worker/main.py:100`, `summary-worker/main.py:123`, `api/embedding_schemas.py:9`.

**Рекомендация.** Для каждого производного результата определить отпечаток обработки: версия входа + версия алгоритма/промпта + существенные параметры. Разделить явные политики «сохранить старый результат» и «перестроить при смене конфигурации». Для разбиения учитывать размер чанка и идентичность токенизатора; сейчас в образе закреплён токенизатор bge-m3 при настраиваемой модели эмбеддингов (`api/Dockerfile:20`).

## 3. Ссылка в PostgreSQL считается доказательством наличия вектора — высокий приоритет для восстановления

**Факт.** Выборка `PENDING_CHUNKS` проверяет только поля PostgreSQL. Если они соответствуют ожидаемой коллекции и ID, наличие точки в Qdrant не проверяется. Поиск считает отсутствующую коллекцию пустым результатом.

**Сценарий:** потеря/удаление коллекции либо восстановление Qdrant из более старого состояния при сохранённых ссылках PostgreSQL. Воркеры пропускают строки как готовые; поиск не видит их. Само включение индексации состояние не исправляет.

Это отличается от обратного сбоя: если Qdrant успел записать вектор, а PostgreSQL не сохранил ссылку, следующий проход повторяет upsert с тем же ID и обычно восстанавливается.

**Основания:** `api/paper_embeddings.py:42`, `api/paper_embeddings.py:173`, `api/chunks.py:119`.

**Рекомендация.** Нужны явный режим rebuild и сверка хранилищ: проверка коллекций/точек, сброс или восстановление устаревших ссылок. Для производного индекса следует описать процедуру полного восстановления из первичных данных.

## 4. Замена чанков удаляет старые векторы раньше фиксации новой версии — средний приоритет

**Факт.** `replace_source_chunks` открывает транзакцию PostgreSQL, удаляет точки во внешних коллекциях Qdrant и лишь затем заменяет строки чанков. Откат SQL-транзакции не отменяет уже выполненные удаления в Qdrant.

**Сценарий:** первая коллекция очищена, удаление во второй завершилось ошибкой либо процесс упал до SQL commit. В PostgreSQL остался прежний набор, в части коллекций его точек уже нет. Повторная обработка источника может восстановить систему, но до её успеха хранилища расходятся. При длительной ошибке это состояние сохраняется.

Даже успешный проход создаёт интервал без векторного результата: новые чанки сначала фиксируются, затем индексируются отдельным этапом.

**Основания:** `api/paper_embeddings.py:77`, `api/paper_embeddings.py:112`, `api/paper_embeddings.py:126`, `api/paper_embeddings.py:173`.

**Рекомендация.** Если нужна доступность прежнего результата до готовности нового, создавать новую генерацию чанков, индексировать её, переключать активную генерацию и затем удалять старую. Для надёжной очистки достаточно отдельной повторяемой операции/задания; общая распределённая транзакция не обязательна. Если временные пробелы допустимы, зафиксировать это как контракт и добавить восстановление из пункта 3.

## 5. `running` имеет разные гарантии восстановления; RAG может остаться в нём навсегда — высокий/средний приоритет

У импорта, текста и саммари есть аренда и повторный захват. У RAG запись `running` обслуживается только живым HTTP-обработчиком.

**Сценарий:** процесс API принудительно остановлен после `start_run` либо PostgreSQL недоступен во время `finish_run`. После перезапуска никто не завершает эту запись. Frontend продолжает опрашивать `running` без собственного предельного срока. Повторный POST с тем же ID получает 409, а не продолжает выполнение.

Отдельно HTTP-клиент RAG создан с `timeout=None`, общего дедлайна выполнения в RAG нет. Обработчик исключения timeout сам по себе не создаёт таймаут: зависший внешний запрос может не завершиться автоматически.

**Основания:** `api/main.py:79`, `api/rag_history.py:44`, `api/rag_history.py:83`, `api/rag.py:393`, `fontend/public/app.js:590`.

**Рекомендация.** RAG не обязан становиться фоновой очередью. Для синхронной модели достаточно общего дедлайна и механизма завершения осиротевших запусков через lease/heartbeat или поколение процесса. Контракт повторного ID стоит определить отдельно: конфликт, возврат существующего результата или возобновление.

## 6. Ошибка этапа означает разное: остановку, вечные повторы или отсутствие статуса — средний приоритет

| Этап | Поведение ошибки |
| --- | --- |
| Импорт | До трёх попыток; затем `failed`. Ошибка одной статьи приводит к повтору задания импорта |
| Текст | Возврат в `downloaded`, повтор через минуту без лимита и сохранённого `last_error` |
| Саммари | До трёх попыток; ошибки входа сразу завершаются `failed`, есть `last_error` |
| Индексация | Неподходящий чанк логируется и снова попадает в следующий проход; постоянного состояния отказа нет |

**Последствие.** Повреждённый HTML может бесконечно извлекаться, отвергаемый чанк — бесконечно отправляться на обработку, а интерфейс показывает только «исходник скачан» или косвенное отсутствие результата. Нельзя единообразно ответить, работа ожидает запуска, отложена после ошибки или требует вмешательства.

**Основания:** `arxiv-grabber/main.py:345`, `arxiv-grabber/main.py:508`, `arxiv-grabber/text_worker.py:73`, `summary-worker/main.py:180`, `api/paper_embeddings.py:155`, `api/paper_embeddings.py:239`.

**Рекомендация.** Согласовать классификацию ошибок, backoff, лимит/условие прекращения и сохраняемые диагностические поля. Лимиты могут различаться по этапам. Для постоянного отказа нужен наблюдаемый статус и команда повторной обработки после исправления причины.

## 7. Ручные и связанные чанки имеют разные жизненные циклы — допустимое различие с заметным последствием

**Факт.** Фоновая индексация выбирает только `current_paper_chunks` через INNER JOIN. Ручные `chunks` не имеют такой связи. Текстовый поиск включает их сразу, семантический — после ручного POST embedding.

**Сценарий:** ручной чанк проиндексирован моделью A → конфигурация переключена на B. Поиск обращается к коллекциям B; автоматический воркер не переносит ручной чанк. Он исчезает из семантического поиска до нового ручного запроса, хотя связанный со статьёй чанк будет обработан автоматически.

**Основания:** `api/chunks.py:92`, `api/chunks.py:142`, `api/chunks.py:181`, `api/chunks.py:272`, `api/paper_embeddings.py:42`.

**Рекомендация.** Либо явно выделить ручные чанки как объекты с ручным обслуживанием и дать команду массовой переиндексации, либо включить их в общий контракт индексации. Сам INSERT чанка не нужно автоматически делать очередью без такого продуктового решения.

## 8. Идентичность задания и история попыток устроены неодинаково — средний приоритет

Импорт сохраняет стабильный ID задания и отдельные строки попыток. Суммаризация хранит счётчик и последний результат в одной строке, а ручной retry `failed` заменяет UUID задания и сбрасывает даты/диагностику. RAG сохраняет каждый запуск отдельно. У извлечения и индексации попытки вообще не представлены отдельными сущностями.

**Последствие.** Понятия «повторить то же задание», «новый запуск» и «пересоздать результат» различаются между API. История неудачной суммаризации после retry теряется из БД; прежний UUID остаётся главным образом в логах.

**Основания:** `postgres/migrations/versions/0027_arxiv_import_attempts.py:15`, `api/paper_summaries.py:58`, `api/rag_history.py:44`.

**Рекомендация.** Описать стабильный ключ работы отдельно от ID запуска/попытки. Не обязательно заводить общий журнал для всех этапов сразу; сначала нужны одинаковые термины и правило сохранения диагностики при retry.

## 9. Один указатель на эмбеддинг при нескольких модельных коллекциях — ограничение модели данных

Коллекции разделены по имени модели, но в `chunks` есть одна пара `qdrant_collection/qdrant_point_id`. Поиск использует её для сопоставления результатов. После индексации моделью B указатель на A заменяется, даже если её вектор физически остался.

**Последствие.** Это схема одной активной модели, а не независимых индексов нескольких моделей. При двух индексаторах с разными конфигурациями глобальная блокировка исключит одновременный проход, но они могут поочерёдно перезаписывать ссылки и считать работу друг друга незавершённой. Для обычного запуска одной модели это не самостоятельный дефект.

Дополнительно `revision` эмбеддинга всегда равен строке `openrouter`. Он обозначает путь получения, но не версию модели; изменения модели под прежним именем не распознаются как повод перестроить индекс.

**Основания:** `api/database.py:26`, `api/chunks.py:142`, `api/chunks.py:234`, `api/paper_embeddings.py:29`, `api/paper_embeddings.py:42`, `api/openrouter_embeddings.py:45`.

**Рекомендация.** Если поддерживается только одна активная модель — закрепить ограничение и процедуру переключения. Если нужны несколько — хранить состояние индекса по `(chunk_id, embedding_profile)`. Не обещать автоматическое обнаружение внешней смены весов: можно использовать управляемую версию профиля индекса.

## 10. Инфраструктура воркера зависит от сборки HTTP-приложения — архитектурный долг

`paper_embeddings.py` импортирует `app, lifespan` из `main`. В итоге индексатор загружает маршруты API и создаёт RAG-клиент/настройки, хотя его задача — разбиение и эмбеддинги. Код LLM для summary-worker переносится копированием отдельных файлов API в Docker-образ. Способы подключения к БД/S3 также реализованы в нескольких местах.

Это не доказанная ошибка исполнения, но границы сервисов не совпадают с границами зависимостей. Изменение инициализации API способно затронуть индексатор без изменения его бизнес-логики.

**Основания:** `api/paper_embeddings.py:23`, `api/main.py:65`, `summary-worker/Dockerfile:13`, `arxiv-grabber/storage.py:9`.

**Рекомендация.** Вынести создание клиентов и конфигурации в небольшие общие модули, а HTTP-приложение и воркеры собирать из них независимо. Начать с устранения импорта `main` из индексатора; для этого не нужны ни новый сервис, ни универсальный framework очередей.

## Что уже сделано последовательно и полезно

- PostgreSQL остаётся источником состояния фоновой работы; отдельный брокер не требуется для исправления перечисленных проблем.
- Импорт и саммари защищают запись результата действующей арендой и идентификатором захвата/попытки.
- Извлечение текста использует ключ по SHA-256 содержимого и проверяет конкретную аренду перед публикацией. Просроченный воркер не перезаписывает актуальную ссылку.
- Разбиение повторно проверяет версию источника под блокировкой после чтения файла.
- Подготовка полного набора чанков фиксируется одной SQL-транзакцией. Проверка нулевого чанка опирается на это свойство; сама по себе такая проверка не доказывает ошибку целостности набора.
- Upsert эмбеддинга повторяем благодаря стабильному ID; ссылки записываются после подтверждения Qdrant.
- Разделение article/summary и фильтрация актуальных чанков уже дают основу для дальнейшего версионирования.

## Предлагаемый порядок изменений

1. **Актуальность:** версия входа саммари, проверка перед публикацией, единое определение `has_summary` и текущих summary-чанков.
2. **Версии обработки:** отпечаток разбиения и явная политика обновления модели/промпта. Добавить управляемую команду пересоздания, не заставляя пользователя портить статусы вручную.
3. **Восстановление:** rebuild/сверка Qdrant; дедлайн RAG и завершение осиротевших запусков.
4. **Эксплуатация:** согласовать ошибки, retry и диагностику. Для API состояния полезно различать «вход не готов», «готов к обработке», «ожидает повтора», «выполняется», «готов актуальный результат», «ошибка».
5. **Границы кода:** общие клиенты и типы без зависимости воркеров от HTTP-приложения. Отдельную универсальную таблицу jobs рассматривать только при реальной потребности в общих операциях над заданиями.

Минимальный общий контракт для этапа: `work_key`, `input_version`, `processing_version`, `attempt/claim`, `available_at`, `lease_until`, `last_error` и ссылка на опубликованный результат. Это логические понятия: не все поля обязаны находиться в одной таблице и называться одинаково.

## Проверки, необходимые при реализации

- Заменить исходник во время генерации саммари: устаревшая попытка не публикуется как текущая.
- Изменить размер чанка при неизменном тексте: источник действительно переразбивается по выбранной политике.
- Удалить тестовую точку/коллекцию Qdrant при сохранённых SQL-ссылках: процедура восстановления возвращает результат в поиск.
- Прервать замену чанков между удалением Qdrant и SQL commit: повторный проход восстанавливает согласованность.
- Принудительно остановить тестовый API после создания RAG run: запуск перестаёт бесконечно считаться живым.
- Подать постоянную ошибку HTML/эмбеддинга: состояние видно, автоматические повторы ограничены выбранной политикой.
- Переключить модель при наличии ручных чанков: поведение соответствует явно принятому контракту.

Эти проверки не выполнялись в рамках статического исследования. Имеющиеся тестовые файлы сосредоточены на OpenRouter и переносе данных; автоматической проверки перечисленных переходов состояния в просмотренных тестах не обнаружено.
