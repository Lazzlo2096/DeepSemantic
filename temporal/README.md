# Temporal без SQL-машины состояний

Workflow владеют состоянием фоновой обработки. В PostgreSQL остаются входные
параметры импортов и готовые артефакты, необходимые каталогу и поиску.

```text
ImportWorkflow: список статей → скачивание HTML → PaperWorkflow
PaperWorkflow: HTML → Markdown
                        ├─ IndexWorkflow: чанки статьи → эмбеддинги → Qdrant
                        └─ SummaryWorkflow: саммари → IndexWorkflow для саммари
```

Переходы, параллельные ветки, повторные попытки и курсоры определены в
`api/processing/workflows.py`. Пауза передаётся Signal `set_paused`, прогресс
читается Query `progress`. Ошибка суммаризации не отменяет индекс статьи.
После завершения импорта его дочерние workflow продолжают работать.

## Управление веткой саммари через REST

После миграции `0040_pipeline_settings` глобальная настройка ветки саммари
хранится в PostgreSQL. Это конфигурация, а не SQL-очередь или статус выполнения.
По умолчанию режим `enabled`, что сохраняет поведение новых импортов.

```sh
# Оставить только HTML → Markdown → чанки статьи → эмбеддинги → Qdrant.
curl -X PUT http://localhost:8000/pipeline/settings \
  -H 'Content-Type: application/json' -d '{"summary_mode":"deferred"}'

# Включить саммари и обработать накопившиеся статьи.
curl -X PUT http://localhost:8000/pipeline/settings \
  -H 'Content-Type: application/json' -d '{"summary_mode":"enabled"}'

curl http://localhost:8000/pipeline/settings
curl http://localhost:8000/pipeline/summary-reconciliation
curl http://localhost:8000/papers/2611.00001v1/processing
```

Через frontend те же пути доступны с префиксом `/api`.

`PaperWorkflow` завершает обработку после индексации статьи; `SummaryWorkflow`
продолжает работать независимо. Для готовности статьи проверяйте
`article_index.status == "completed"` в `/papers/{arxiv_id}/processing`.
Готовность всей ветки саммари — `summary_index.status == "completed"`;
одного наличия текста саммари недостаточно. Ответ содержит `chunks_total`,
`chunks_indexed`, `summary_available` и состояние Temporal незавершённой ветки.
Счётчики индексации основаны на подтверждённых ссылках PostgreSQL на Qdrant.
Удаление точек напрямую в Qdrant при сохранённых ссылках требует явной
перестройки через `processing.manage --rebuild`, как и раньше.

`deferred` запрещает новые операции суммаризации, подготовки и индексации
саммари даже при запущенных вычислительных воркерах. Уже начавшийся вызов LLM
или батч эмбеддингов может завершиться; дальнейшие этапы проверяют режим снова.
`POST /papers/{arxiv_id}/summary` в этом режиме возвращает `deferred`, если
готового саммари нет. Статьи и их векторы продолжают обрабатываться.

Первый `PUT /pipeline/settings` запускает постоянный Temporal workflow
`pipeline:summary-reconciler`. После включения он проходит весь каталог
страницами, включая исторические статьи без Markdown, создаёт недостающие
саммари и восстанавливает незавершённую индексацию. Готовые результаты нужных
версий и параметров используются повторно. Успешно закрытые workflow с тем же
ID не блокируют восстановление: допускается новый Run с проверкой артефактов.
Запущенная обработка с тем же ID используется совместно.

Сверка повторяется каждые 60 секунд, поэтому захватывает статьи, появившиеся
во время прохода, и переживает потерянный сигнал после изменения настройки.
Настройка сохраняется после перезапуска API и воркеров. Ошибки отдельных
саммари видны в `/papers/{arxiv_id}/processing` и Temporal; после исчерпания
Activity retries автоматические платные запуски той же генерации не повторяются
до следующего `PUT` настройки или явного запроса создания саммари. Ошибки
самой сверки отображаются в `runtime.progress.last_error`.

Первое включение сверки — явное разрешение обработать накопленный каталог
с текущими моделями и параметрами. Все этапы, включая скачивание, Markdown,
саммари и индексацию, обслуживает работающий `temporal-orchestrator`.
Файлы с ошибками чтения/преобразования остаются ошибками в Temporal, а не
считаются успешно обработанными.

При обновлении примените миграцию и обновите API вместе с оркестратором. Новые ветвления существующих workflow защищены
Temporal patch markers. Истории ранее успешно закрытых workflow не изменяются.

## Что удаляется из PostgreSQL

Миграция `0039_temporal_native_state` продолжает `0038`. Она предназначена для
этой ветки, а не для отклонённого коммита с `0039_temporal_pipelines`.

| Объект | Изменение |
| --- | --- |
| `temporal_jobs` | Удаляется целиком: SQL-журнал выполнения больше не нужен |
| `paper_index_state` | Удаляется: владение попыткой индексации не хранится в SQL |
| `arxiv_import_items` | Удаляется: манифест статей хранится файлом в RustFS |
| `arxiv_import_attempts` | Удаляется: попытки и счётчики находятся в Temporal |
| `arxiv_imports` | Удаляются `status`, `attempts`, `available_at`, `lease_until`, `claim_id`, `started_at`, `finished_at`, `temporal_discovered` |
| `arxiv_papers` | Удаляются `status`, `lease_until`, `text_available_at` |
| `paper_summaries` | Удаляются `status`, `attempts`, `available_at`, `lease_until`, `parts_completed`, `parts_total`, `last_error`, `created_at` |
| Enum статусов и `arxiv_import_result` | Удаляются |

`arxiv_imports` сохраняет UUID, даты, бакет, фильтр, время создания и ссылку
`workflow_id`: это каталог неизменяемых входных запросов, а не очередь. Воркеры
не опрашивают эту таблицу. Старые параметры импортов остаются доступными после
истечения retention Temporal; если история отсутствует, API возвращает `unknown`.

`paper_summaries` содержит только готовые тексты с ID результата, моделью,
промптом, версией исходника и `generated_at` вместо `finished_at`. Пустые строки
старых queued/running/failed-запросов удаляются; сохранённые тексты не удаляются.
У старых саммари без `source_version` нельзя подтвердить актуальность: они остаются
в БД, но не включаются в текущий поиск до явного повторного создания.

Поле `generation` у саммари и чанков — отпечаток входных данных и конфигурации
результата. Оно не является статусом или владельцем задания. Ссылки на файлы
RustFS и точки Qdrant также остаются данными каталога.

API по-прежнему может возвращать `paper.status`, но вычисляет его из наличия
Markdown: `downloaded` либо `texted`. Промежуточного SQL-статуса `texting` нет.

## Где находится код

- `processing/workflows.py`: состояние и порядок выполнения, дочерние workflow.
- `processing/activities.py`: HTTP, S3, LLM и вызовы сохранения артефактов.
- `processing/arxiv.py`, `html_text.py`, `paper_embeddings.py`, `summarizer.py`: обработка данных.
- `api/paper_repository.py`: чтение и запись данных статей, результатов и чанков.
- `api/temporal_runtime.py`: запуск, сигналы и чтение состояния Temporal для API.

В `api/processing/` нет SQL-запросов к состояниям выполнения. `finish_job`, SQL
аренды и dispatcher удалены. Таблицы логов синхронного RAG не относятся к этому
конвейеру и сохраняются.

## Запросы из API

`POST /arxiv/imports` сохраняет неизменяемые параметры запроса и запускает
`ImportWorkflow` напрямую. HTTP 202 возвращается после подтверждения Temporal.
Если Temporal недоступен, API возвращает 503. Автоматической локальной очереди нет.

Передавайте `request_id` (UUID), чтобы безопасно повторить отправку после потери
ответа. Интерфейс генерирует его заранее и использует повторно при ошибке.
Один UUID нельзя использовать с другим диапазоном дат, бакетом или фильтром.
Параметры запроса могут быть сохранены и без подтверждённого запуска: такой запрос
показывается как `unknown`, его можно запустить кнопкой «Запустить».

`GET /arxiv/imports` объединяет параметры из каталога с описанием и Query Temporal;
статусы и счётчики обратно в SQL не записываются. `pause`/`resume` отправляют Signal.
Повтор после ошибки создаёт новый Run Temporal и использует уже скачанные файлы.

`POST /papers/{arxiv_id}/summary` запускает `SummaryWorkflow`. `GET` читает готовый
результат из БД или состояние workflow из Temporal. SQL-строка при постановке
саммари в очередь не создаётся. Ошибка генерации тоже не создаёт строку результата.

## Импорт и восстановление

Список найденных статей сохраняется в `imports/<UUID>/manifest.json` в RustFS.
Workflow читает его небольшими страницами, хранит текущую позицию и счётчики
в своей истории, использует Continue-As-New каждые 100 статей. Прогресс не
записывается в SQL. Полные тексты, саммари и векторы не передаются через историю.

Готовые саммари и ссылки эмбеддингов используются повторно. Workflow ID,
полученные из версии исходника и параметров, предотвращают одновременный запуск
одинакового конвейера. Для уже работающей зависимости результат читается из
Temporal. Все реплики вычислительных воркеров должны использовать одинаковую
конфигурацию. Оркестратор запускайте в одной реплике; очередь импорта
внутри него ограничена одной одновременной Activity для контроля HTTP-трафика.

Временные ошибки Activities повторяются до трёх раз. Исчерпанные попытки,
ошибки входа и отмена видны в Temporal UI. SQL-транзакции защищают публикацию
артефактов и их актуальность, но не заменяют механизм выполнения.

## Развёртывание

Это изменение несовместимо с открытыми SQL-зависимыми `ProcessingWorkflow` старой
версии. Перед миграцией завершите их старым стеком или явно прекратите через
Temporal UI и сохраните резервную копию. В том числе нужно остановить старые API,
SQL-dispatcher и воркеры. Не запускайте их после применения `0039`.

```sh
# Старой ревизией, пока хранилища запущены:
just backup
# Затем переключитесь на новую ревизию:
just up-server
# Все обработчики запускаются автоматически внутри temporal-orchestrator.
```

Старые незавершённые запросы не превращаются в SQL-очередь: их можно повторно
запустить из сохранённых параметров. Обработка существующего каталога запускается
явно, без автоматического платного пересоздания саммари при миграции:

```sh
docker compose exec temporal-orchestrator python -m processing.manage --reprocess-catalog
```

Этот запуск использует текущие модели и параметры и может создать новые саммари
для результатов без подтверждённой версии входа.

`temporal-orchestrator` постоянно исполняет workflow и Activities всех пяти
очередей (`pipeline`, `import`, `text`, `summary`, `index`) в одном процессе.
Для каждой очереди сохраняется собственный лимит одновременных Activities.
Четыре отдельных вычислительных контейнера удалены из Compose.
Сервис `temporal-dispatcher` удалён. `just up` удаляет его контейнер через
`--remove-orphans`. [Temporal UI](http://127.0.0.1:8088) доступен через localhost;
для сервера используйте SSH-туннель.

## Повтор и перестройка

Workflow ID теперь берётся из Temporal UI, а не из SQL-журнала:

```sh
docker compose exec temporal-orchestrator python -m processing.manage --retry 'summary:...'
docker compose exec temporal-orchestrator python -m processing.manage --rebuild 'index:...'
```

Перестройка повторно записывает векторы, даже если ссылки PostgreSQL заполнены.
При обычной обработке отсутствие коллекции само по себе не инициирует перестройку.
Версии исходников защищают новые результаты от поздних старых попыток.

Temporal не делает PostgreSQL, RustFS и Qdrant общей транзакцией. Сбой между
ответом LLM и сохранением текста может привести к повторной оплате. При замене
чанков остаётся временное окно без старых векторов.

История Temporal хранится в `temporal-postgres-data`, retention закрытых запусков —
30 дней. `just backup` сохраняет этот том вместе с основным дампом и RustFS;
восстанавливать их нужно совместно. Обратная миграция требует восстановления
соответствующей резервной копии. Проверки новой реализации автоматически не запускаются.
