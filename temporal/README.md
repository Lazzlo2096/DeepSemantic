# Фоновые процессы на Temporal

Импорт, извлечение Markdown, суммаризация и индексация выполняются через Temporal
Python SDK. RAG сайта продолжает использовать LangGraph внутри HTTP-запроса;
Studio и его checkpoints работают отдельно.

## Запуск и обновление

Перед первым обновлением с SQL-воркеров создайте резервную копию старой ревизией
проекта (`just backup`), пока старый PostgreSQL запущен. Команда оставляет сервисы
остановленными. Затем обновите код и выполните:

```sh
just up-server
# Включите нужные воркеры на странице «Воркеры» либо запустите все:
docker compose -f compose.yaml -f compose.server.yaml --profile workers up -d arxiv-grabber arxiv-text-worker summary-worker embeding-worker
```

Миграция `0038` требует остановленных старых API и воркеров: они больше не должны
писать SQL-аренды. Она снимает ограничения аренды, возвращает незавершённую работу
в очередь и сохраняет статьи, чанки, историю и результаты. Старые столбцы аренды
остаются для совместимости схемы, но больше не управляют исполнением.
Обратная миграция запрещена: для возврата нужна старая ревизия и резервная копия.

У старых саммари неизвестна версия входа. При первом запуске dispatcher создаст
для них новые запросы; включение summary-worker приведёт к повторным платным
вызовам модели. Индексация также один раз проходит существующие источники для
формирования новой истории выполнения. Воркеры по умолчанию создаются выключенными.

`just up` запускает Temporal, его отдельный PostgreSQL, UI и dispatcher. Четыре
вычислительных воркера по-прежнему можно включать и выключать независимо.
Все они собираются из `temporal/Dockerfile`; их имена в Compose и интерфейсе сохранены.

[Temporal UI](http://127.0.0.1:8088) доступен только через localhost. На удалённом
сервере используйте SSH-туннель `ssh -N -L 8088:127.0.0.1:8088 user@server`.
Порты задаются `TEMPORAL_PORT` (7233) и `TEMPORAL_UI_PORT` (8088).

## Контракт исполнения

- Dispatcher каждые пять секунд материализует сохранённые запросы и новые версии
  источников в `temporal_jobs`, затем отправляет их в Temporal. Доступность Temporal
  не требуется для приёма запроса API. Стабильный Workflow ID и запрет повторного
  старта закрывают сбой между отправкой и подтверждением в SQL.
- PostgreSQL хранит результаты и статусы для сайта; Temporal владеет попытками,
  таймерами и восстановлением исполнения. `temporal_jobs` также хранит ошибки
  завершённых заданий. Перезапуск dispatcher не перезапускает завершённые работы.
- Очереди: `deepsemantic-import`, `deepsemantic-text`, `deepsemantic-summary`,
  `deepsemantic-index`. По умолчанию каждый процесс выполняет одну Activity
  одновременно; `TEMPORAL_ACTIVITY_CONCURRENCY` позволяет изменить лимит.
- Импорт сохраняет список статей в `arxiv_import_items` и загружает по одной статье
  на Activity. Прогресс фиксируется в PostgreSQL. Пауза действует после текущей
  операции; обнаружение списка также должно завершиться. Продолжение использует
  сохранённый список. Общая advisory-блокировка сериализует запросы к arXiv.
- Текст публикуется только для захваченной версии исходника. Саммари привязано
  к UUID запроса и версии Markdown; устаревшая попытка не может заменить актуальное
  саммари. Устаревшие саммари сразу исключаются из источников поиска.
- У задания индексации зафиксированы версия источника, модель, размер чанка и
  версия алгоритма разбиения. Для нового сочетания создаётся новое задание.
  Индексация выполняется пакетами по восемь чанков с сохранением курсора.
- Импорт и длинная индексация используют Continue-As-New каждые 100 итераций,
  чтобы история исполнения не росла без ограничения. Полные статьи, результаты
  LLM, векторы и список статей не передаются через Event History.
- Временные ошибки Activity повторяются до трёх раз, начиная с задержки 10 секунд.
  Ошибки входа, превышение контекста и отклонённые чанки завершаются без повторов.
  Запись конечного статуса повторяется до восстановления PostgreSQL.

Смена модели или промпта суммаризации сохраняет уже готовые саммари. Новый исходный
текст или ручной повтор неуспешного запроса создаёт новую обработку. Параметры
модели для уже поставленного задания не меняются при перезапуске воркера.

Остановка контейнера приостанавливает потребление его очереди. Задания остаются
в Temporal и восстанавливаются после запуска; это отличается от бизнес-паузы
конкретного импорта. Прямой CLI `arxiv-grabber/main.py --from ... --to ...` оставлен
для разовой загрузки без Temporal; старые циклы SQL-очередей удалены.

## Повтор и восстановление индекса

В UI Temporal или SQL найдите Workflow ID из `temporal_jobs.id`. Повтор завершённого
с ошибкой задания создаёт новый Workflow ID и сохраняет историю исходной ошибки:

```sh
docker compose exec temporal-dispatcher python -m processing.dispatcher --retry 'summary:...'
```

Для саммари также работает прежний `POST /papers/{arxiv_id}/summary`.
Если Qdrant потерял точки, можно повторно построить завершённое задание индекса:

```sh
docker compose exec temporal-dispatcher python -m processing.dispatcher --rebuild 'index:...'
```

Перестройка заново записывает все пакеты источника, даже если ссылки PostgreSQL
считают их готовыми. Повтор старой версии источника ничего не публикует: используйте
задание актуальной версии. Отсутствие коллекций само по себе не запускает перестройку.

Temporal не делает операции PostgreSQL, RustFS и Qdrant общей транзакцией.
Повторяемые записи и проверка версии защищают публикацию результата; при замене
чанков сохраняется временное окно без старых векторов. Вызов LLM тоже может быть
оплачен повторно при сбое между ответом провайдера и сохранением результата.
Сохранённое саммари повторно не генерируется при повторе той же Activity.

## Эксплуатация

Compose использует закреплённые образы Temporal `1.29.1` и UI `2.34.0`, с SQL
persistence и visibility в отдельном PostgreSQL 17. Это один узел без высокой
доступности. Auto-setup инициализирует и обновляет схемы при старте; обновления
версий сервера нужно предварительно проверять на копии данных. Сервер доступен
внутри сети Compose и через localhost; наружу gRPC и UI не публикуйте без защиты.

История Temporal находится в `temporal-postgres-data`. `just backup` останавливает
сервисы и включает этот том в холодную копию вместе с основным дампом и остальными
хранилищами. Восстанавливайте их совместно: один основной дамп PostgreSQL не содержит
историю Temporal. Retention закрытых workflow — 30 дней; `temporal_jobs` сохраняется
в основной БД независимо от retention.

При изменении последовательности Activities проверяйте replay сохранённых историй
и используйте версионирование workflow. Внешние вызовы выполняются только в Activities.

## Проверки

```sh
python -m pip install -r api/requirements.txt -r arxiv-grabber/requirements.txt -r temporal/requirements.txt
python -m unittest discover -s tests -v
python tests/temporal/run.py
```

Последняя команда собирает образ и запускает отдельный Compose-проект без портов
и боевых volumes. Проверяет обновление с `0037` на данных с арендами, конвейер через
настоящие PostgreSQL/RustFS/Qdrant/Temporal, паузу, повтор отправки, смену исходника,
восстановление на новом воркере и replay. arXiv и платные вызовы модели подменены.
